# 154 — 27 Nov 2026: speed work (no model change)

The user asked, outside the pass sequence, whether the simulations could run on the GPU (CUDA) because testing takes
long, and then asked for the two CPU-side changes proposed instead. Nothing in the model changed: every run is
bit-identical to before, so the next sweep's borrowed control still matches its reference. Pass 113 (STATE) is still
next.

## 1. Where the time goes (measured before any change)

- One n = 217 run alone: about 2.5 s a step, so about 10.5 min for 250 Myr. In a sweep, 8 runs at once take about
  20 min each (4.8 s a step): 8 workers on the 8-core Ryzen 7 9800X3D give about 4× throughput, not 8×.
- The last sweep (Transfer confirmation, 47 min): tests 6 min, runs 43.5 min, reviews 3.5 min.
- A step's time is spread thin. With the compiled kernels made visible to the profiler (15 steps, seed 9999, after a
  3-step warm-up), the largest single item is the crust flow's edge diffusivity (9%), then the nearest-node lookup
  (8%), ducc0's transforms (12% together), the remap's return (6%), the nearest-label Dijkstra (6%), the hotspot discs
  (5%), the raster update (4%), the sediment column's Newton solve (3%); about 35 functions make up 90%.

## 2. The GPU question: not pursued

A port would have to move nearly the whole plate layer (about 6,000 lines) onto the GPU, since no part holds enough
of the time to pay for host–device transfers on its own. Several parts are sequential by nature (priority flood,
drainage routing, the Dijkstra searches, the rift-line search, the plate events). The RTX 3070 does 64-bit arithmetic
at 1/64 of its 32-bit rate, and the world fields and ledgers are 64-bit. GPU results would not match the CPU's bit
for bit, so the borrowed control, the identity checks and every reference run would need a new base, and parallel
sums on a GPU can differ from run to run unless written with care. And one GPU runs a sweep's 12 runs one after
another where the CPU runs 8 at once: each run would have to take under about 2.5 min just to break even. The
expected gain, from parity to about 2× after weeks of work, does not justify losing the repeatability the method
rests on.

## 3. What was done

**Tests in parallel.** `scripts.run_sweep` runs the sweep's tests with pytest-xdist on 8 workers, test by test
(`TEST_WORKERS` 8, each worker's kernels on `TEST_THREADS` 2 threads through `NUMBA_NUM_THREADS`); without
pytest-xdist it runs them in one process as before. The sweep subset took 6:00 in one process, 3:04 on 8 workers
grouped by file, 1:33 on 8 test by test, and 1:43 on 14. The whole suite (386 tests) takes 1:38 on 8. The coupling
tests' fixed folders under `outputs/test-tmp/` now carry the worker's name, so two workers never clear each other's
files. pytest-xdist is in `requirements-dev.txt`; the timing record of the test step now carries its worker count, and
the prediction reads records with the same count.

**Kernels, bit-identical by construction.** Only changes that cannot alter a result:

- `prange` (numba `parallel=True`) over independent iterations only: the nearest-node lookup
  (`fields.nearest_entries`, one point per iteration), the crust flow's edge diffusivity (`crust_flow.edge_kappa`:
  each edge is written by one node only; the largest value is a max and the counts are integers), its diffusion step
  (`diffuse_edges`, one node per iteration) and its flux table (`_flux_table`, one row of crust thickness per
  iteration, each with its own work arrays). No floating-point sum is split across threads.
  `planet_grid.jit.set_threads` sets the kernels' thread count from the run's `threads` (sweeps: 2; a bare run:
  all cores, capped by `NUMBA_NUM_THREADS`), called in `PlateSim.__init__`.
- Caches of pure functions: the forward map (plate node to nearest world node) is a function of the plate's rotation
  only, so `_forward_nodes` keeps it for the step by the rotation's bytes (read by `_opened_area`, `_update_rasters`
  and the split and merge events); a hotspot's Gaussian discs are functions of its fixed mantle-frame position and the
  radius, so `Mantle._disc` keeps them while the hotspot lives. Both arrays are read-only.

Tried and dropped: an array-based heap for the Dijkstra searches (it pops in heapq's exact order, so it is
identical) was only 10–20% faster on a search that holds 6% of a step: not worth the code.

## 4. The identity check (rule written before reading)

Question: do the changed kernels leave every run bit-identical? Rule: an md5 per step of every `state()` array, every
plate's rasters, the mantle flow's coefficients and the ledgers (`erosion_totals`), compared step by step with the
same fingerprint from the code before the change; any difference rejects the change. Cases: n = 48, seed 7, 70 steps
at `threads` 1 and 2 (as `precheck-p104-repeat/rep.py`), and n = 217, seed 9999, 60 steps at `threads` 2.
Scripts: `outputs/planet-calibration/precheck-speed/ident.py`, `compare.py`.

Result: **identical** in all three cases, on the final code. (The two baselines at 1 and 2 threads were identical to
each other as well.) `tests/test_parallel_kernels.py` (in the sweep subset) checks the lookup, the edge diffusivity
and the diffusion step at 1 and 4 threads, and that the caches return what they replace.

## 5. The gain (paired against the old code in a separate checkout; `precheck-speed/timing.py`)

| Case | Before | After | |
|---|---|---|---|
| one run alone, `threads` 2 (seed 9999, 30 steps, twice) | 2.46 s/step | 2.12 s/step | −14% |
| one run alone, all cores | 2.52 | 2.10 | −17% |
| 8 runs at once, `threads` 2, as in a sweep (25 steps each) | 4.32 (mean) | 3.95 | −9% (wall 134 → 119 s) |

So a sweep's runs gain about 9%, less than the 1.3–2× first guessed: the kernels that parallelise hold little of the
time, and in a sweep each worker has only its core's second thread to spare. With the tests at 1.5 min, a borrowed
sweep of 12 runs should take about 38 min instead of 47. A larger gain would need changes that alter results (any
reordered sum, or numpy code moved into numba, whose exp and log can differ in the last bit), and so a new base for
every reference run; not done.
